# App windows

Prefix: `WIN`. Owner docs: [design/mac-redesign.md](../design/mac-redesign.md) §3.7 and §3.9, [UX.md](../UX.md) § "macOS app" 2 and § "Opening a window", [DESIGN.md](../DESIGN.md) "App windows", [design/dragdrop.md](../design/dragdrop.md) (the drop pill), [NFR.md](../NFR.md). Last reviewed: 2026-11-04, against main `5b492191` (adopt: WIN-44…49, an app's own "New window" becomes another Mac window).

## Purpose

One Mac window per app running on the phone: the phone launches that app on a virtual display whose size the window asks for, and the window draws its stream. It is how a person uses a phone app with a mouse and keyboard, alongside the Phone Mirror (the phone's own screen, MIRROR) and the Deck (the launcher, DECK). A window is a view of one app on the phone **in use**: it starts nothing else, changes no phone setting, and outlives nothing — closing it closes that app's stream, not the app's data and not the session. One app on one phone has one window: asking for it again raises it (`WindowManager.openOrRaise`, WIN-2).

An app that the phone can run more than once may have **several windows**, one per task, but only when the person asks for another: a click always raises the app's existing window (WIN-2, WIN-36), and ⌘N, File ▸ New <App> Window, the Dock shim's menu or the Deck cell's menu adds one (WIN-25, WIN-26). An app that starts a window of its own on the phone — a browser's "New window" — is the same request made inside the app: the phone reports the task and the Mac's own New-item rule decides whether to open one more Mac window for it (WIN-44…WIN-46). Every window is its own stream, its own virtual display and its own task on the phone; closing one ends only that task (WIN-31). Windows have no tabs and are not restored after a relaunch (Non-goals). The evidence for what the phone allows, and its cost, is `.agent/multiwin/spike.md`.

The same AppKit window kind carries three subjects: an app (`AppWindowController`, the one this spec is about), a link (`LinkWindowController`, `design/links.md`) and a handoff window (`HandoffWindowController`, `design/handoff.md`). They share the chrome, the input mapper, the opening cover, the resize rules and the picture watchdog; they differ in what they show and in how their style and frame are remembered (a link or handoff window has one frame, an app window one per package).

## User stories

| ID | Priority | Story |
|---|---|---|
| WIN-S1 | P1 | As a person with a phone, I want an app in its own window so that I can use it with the Mac's keyboard and pointer while the phone stays where it is. |
| WIN-S2 | P1 | As a person opening one, I want to see that it is opening and, if it will not, why and what to try, so that a black window is never the answer. |
| WIN-S3 | P1 | As a person with two phones, I want the window's title to name the app and the phone so that I know which phone it acts on. |
| WIN-S4 | P2 | As a person, I want the window's chrome out of the way (immersive) or always there (framed), remembered per app, so that I do not choose again each time. |
| WIN-S5 | P2 | As a person, I want an app too small or too large for the Mac's screen to keep its layout by changing its density, so that the app is readable. |
| WIN-S6 | P1 | As a person resizing the window, I want the picture to stay correct on every frame so that a drag never shows black bands or a clipped app. |
| WIN-S7 | P1 | As a person, I want the window back where and how big I left it so that reopening is not a new setup. |
| WIN-S8 | P1 | As a person, I want closing the window to end only that window so that my other work and the connection survive. |
| WIN-S9 | P2 | As a person whose phone went away, I want the window to say so and come back on its own so that I know whether the picture is live. |
| WIN-S10 | P2 | As a person with a large screen, I want an app window full screen so that the app uses the space. |
| WIN-S11 | P1 | As a person using an app that supports several windows, I want a second window when I ask for one so that I can keep two pages or two conversations side by side on the Mac. |
| WIN-S12 | P1 | As a person, I want a click to raise the app's window and only a New Window command to make another, so that I never collect windows by accident. |
| WIN-S13 | P1 | As a person with several windows of one app, I want each named after its task and one key to cycle them, so that I can tell them apart and reach the one I mean. |
| WIN-S14 | P1 | As a person whose app opens one window at a time, I want to be told so where I asked, so that I do not wait for a window that cannot come. |
| WIN-S15 | P2 | As a person, I want a limit on how many windows my phone runs at once, so that it stays cool and my Mac stays fast. |

## States and events

The window has one lifecycle (`Opening` → `Live` → closed) whose picture states are `PhoneScreenOverlay`-like covers of its own (`OpeningCover`, and the disconnection overlay for a stall or a dropped link), one style value, one density value and one placement. The style and density are stored values, not modes: each window reads them at open. The picture's own states are one machine (WIN-16, WIN-17, WIN-39): `Live` → `Stalled` on 1.5 s of silence without a frame or a `window.still`, `Live`/`Stalled` → `Link down` (silent for 1 s) → `Reconnecting` (1 s) → `Phone offline` (15 s), and a frame, a `still` or a reconnect returns to `Live`.

| State | Event | Result |
|---|---|---|
| Opening (no frame) / Live | `any entry point asks for that app again` | the window is raised (un-minimised, key, front); no second `window.open` (WIN-2) |
| Opening (no frame) | `first frame` | Live; the cover is gone for good |
| Opening | `5 s` / `20 s` | Slow: "Taking longer than usual" + Cancel / Failed: grey icon, "<phone> can't open <app>." + reason + Close; frozen |
| Opening / Slow | `Cancel` | the window closes (its `window.close` cancels the open on the phone) |
| Opening / Slow | `the phone's error` | Failed at once with the mapped reason; no Try Again |
| Live | `window.resize` sent | the last frame fills the window until the answer (≤ 2 s); a request equal to the one in flight or the last one sent is not sent at all |
| Live | `⌘+ / ⌘−` at the clamp | nothing: the press cannot change the density, so no request is made |
| Live | `answer frame` | the picture is the answer's; normal aspect rule |
| Live | `frames and stills stop 1.5 s` | Stalled: the disconnection overlay "Not responding", with the icon and "Waiting for <phone>…" (WIN-39), phone-side controls frozen |
| Stalled | `a frame or a still` | Live; the overlay goes and the bar's mirror is live again |
| Live / Stalled | `link lost` | Link down: nothing for 1 s, then the overlay "Reconnecting…" and "Phone offline" at 15 s; input dropped |
| Link down / Reconnecting / Offline | `a late frame` | Live; the overlay goes |
| any | `link returns` | Live; the overlay goes and the window re-sends its `window.open` |
| Live | `minimised / occluded` | `window.pause`; the watchdog's clock idles |
| Paused | `visible again` | `window.resume`; the clock restarts from now |
| Live | `style switch (⌥⌘F, menu)` | the window grows or shrinks by the bar; the choice is stored |
| Live | `⌘+ / ⌘− / ⌘0` | the app's density steps or clears; one `window.resize` |
| any | `⌘W / close light` | `window.close`; the window leaves the manager; nothing else is ever sent for that stream (WIN-38) |
| any | `phone closed the stream` (`window.closed`) | the window closes without sending `window.close` |
| any | `error no_stream` and no window for the stream | nothing visible; the log says so (WIN-38) |
| Opening / Slow | `error no_stream` | the cover's refusal, Close alone (WIN-11, WIN-38) |
| Live / Stalled | `error no_stream` | the window closes as on `window.closed`, sending no `window.close` back (WIN-12, WIN-38) |
| Live | `⌘Q` | every window closes; the app quits |

Ignored events, stated so nobody builds them: a second open of an app whose window is already up (it raises, WIN-2), a resize request that arrives during the live drag (it waits for the drag's end), a style or density switch while full screen (only the memory moves, the layout applies on exit), a ⌘+/⌘− on a window with no app package, and any input while the cover, the stall or the link down is up.

### An app's windows on one phone

The windows of one app on the phone in use are one small machine; each window
still has its own lifecycle above, and the style, density and frame stay the
app's (WIN-7, WIN-10, WIN-13).

| State | Event | Result |
|---|---|---|
| None | `click` (Deck cell, Dock shim, Spotlight, notification, Shortcuts, MCP, debug) | One: open a window and send one `window.open` |
| None · One · Several | `New Window` (⌘N, File, Dock, Deck) | one more window and one `window.open` with `newInstance` |
| One · Several | `click` | raise the frontmost window; no `window.open` |
| Several | ⌘` | raise the next window of that app in front-to-back order, wrapping |
| Several | `a window closes` | one fewer window; only that task ends on the phone |
| Several → One | `the second-to-last window closes` | the survivor retitles to "<App> (<phone>)" |
| any | `a task label arrives` | that window retitles; the Dock and Deck menus re-list |
| any at the cap | `New Window` | ignored; the item reads "Close a <App> window to open another." |
| any | `the phone says the app opens one window` | ignored; the item reads "<App> opens one window at a time." |
| any | `a window of that app is opening` | `New Window` ignored; the item reads "Opening on your phone…" |
| any | `link lost` | every window keeps its frame and the disconnection overlay; `New Window` ignored ("Reconnecting…", then "Phone offline") |
| any | `link returns` | one `window.open` per window, front to back, `newInstance` on all but the first |
| any | `the phone ends a task on its own` (`window.closed`) | that window closes; the others stay |
| any | `the phone refuses the new window` (`error too_many_windows`) | that window closes; the Deck's banner reads "Close a <App> window to open another." |
| One · Several | `the app started another task` (`window.task`, WIN-44) | the New item decides: one more window and one `window.adopt`, or nothing (WIN-45) |
| One · Several at the Mac's cap | `the app started another task` | no window; the Deck's banner reads "Close a <App> window to open another." |
| Opening | `the phone refuses the adopt` (`error cannot_adopt`) | that window closes quietly; nothing is sent back |
| any | `the phone moved that window's task to its own screen` (`window.closed` `moved_to_phone`) | that window closes quietly; the others stay |

Ignored events here too: ⌘` with one window, `New Window` for the Phone Mirror
(it has no app), a `click` while the phone is offline or the Deck is in
Welcome/Nearby, a picked window item for a window already front, and a
`newInstance` open for an app the phone says opens one window.

### A task arrives on the phone

The phone's own machine (WIN-44, WIN-48, WIN-49) has two states: `Idle` (no app
stream is open, so nothing can be reported) and `Watching` (at least one app
stream is open). It accepts task-stack events, its own launches and moves, and
the open streams; it returns reports, closes and nothing, and never performs a
side effect itself. Its facts are the streams' own task ids and displays, the
task ids the phone launched or moved, the ids already reported and the last
report time per package.

| State | Event | Result |
|---|---|---|
| Idle | any task-stack event | nothing |
| Idle | `an app stream opens` | Watching |
| Watching | `the phone's own launch or move starts` / finishes | that task id is marked the phone's own; it is never reported |
| Watching | `onTaskCreated` with a fresh id of a package that has a stream, not the phone's own | one `window.task` for that stream, at most once a second per package; the task stays where it is |
| Watching | the same id again (`onTaskCreated` repeats) | nothing (once per task) |
| Watching | `onTaskCreated` of a package with no stream, or one the phone launched | nothing |
| Watching | `onTaskDisplayChanged` with a stream's own task id, to another display | nothing yet; if it went to the phone's display, ask whether the streamed display still has a task |
| Watching | that display still has a task | nothing: the stream shows what the display shows |
| Watching | that display is empty | close that stream `moved_to_phone` |
| Watching | `onTaskRemoved` with a stream's own task id | ask whether the display still has a task (WIN-50) |
| Watching | the display has another task on top | the stream follows that task id and its title; nothing is sent as a close |
| Watching | the display has no task, with no move | close that stream `app_exited` |
| Watching | the display has no task after a move probe | close that stream `moved_to_phone` |
| Watching | `the last app stream closes` | Idle; the facts are forgotten |

## Assumptions

- The phone runs API 34+ and can create a virtual display at the shell UID (`docs/design/phone-mirror.md`); an app window is that display's stream.
- Several instances of one app come from `FLAG_ACTIVITY_NEW_DOCUMENT | FLAG_ACTIVITY_MULTIPLE_TASK` on the launch Intent, and the activity's own `launchMode`/`documentLaunchMode` still decides whether a second task appears (`.agent/multiwin/spike.md`). Chrome's launcher is `singleInstancePerTask` and declares `android.window.PROPERTY_SUPPORTS_MULTI_INSTANCE_SYSTEM_UI` — the one app on the emulator image that does.
- `PackageManager.getProperty("android.window.PROPERTY_SUPPORTS_MULTI_INSTANCE_SYSTEM_UI", ComponentName)` reads the app's or the launcher activity's declaration (the constant's name is API 35+; the phone is API 34+, so the name is passed as a string).
- The phone reads a task's label from `RecentTaskInfo.taskDescription` on the same hidden `IActivityTaskManager` the window observer already uses; a phone that cannot read it sends no label and the app's own label stands.
- Four app windows per phone is the cap until a real phone's encoder says otherwise; the emulator's software encoder measures the shape of the cost, not a phone's numbers (`spike.md`).
- The app's label comes from the cached app list; before it arrives the window is titled with the package's last part, and the phone's `window.title` corrects it.
- 1280×800 is the smallest supported screen; the window's own minimum is a 320×240 pt stream plus the bar.
- The window's style and density are stored in the active profile's defaults (`chrome.style.<pkg>`, `chrome.density.<pkg>`), never in the person's default domain.
- A link window and a handoff window share this window kind but are remembered under one frame each (`link`, `handoff`), and their subjects are `design/links.md`'s and `design/handoff.md`'s.

## Non-goals

- The Phone Mirror: the phone's own screen is MIRROR's window, not an app window.
- Launching an app from a window, a second launcher, or several windows of one app **by default**: a click raises, and a new window is only ever the person's request (WIN-2, WIN-25).
- Window tabs, a window picker, several apps in one window, picture-in-picture, or merging two windows into one: a later idea, not this change.
- Restoring a window's task (its scroll, its page, its position in the app) or its Z-order after a relaunch or a reconnect: the phone owns the app and its tasks.
- A per-window style, density or frame: style, density and the remembered frame stay the app's.
- The reverse cycle (⇧⌘`) and a menu of a specific window's own actions.
- Several instances on the phone's own screen (display 0) or in the phone's Recents as a feature.
- A Dock icon or ⌘-Tab entry of its own: the Dock identity is `design/dock.md`'s surface (`DOCK`), one per app, however many windows it has.
- Live Text, Show Touches, the style/density menus and the Shortcuts/App Intents entries: their own surfaces (MENU, `LIVETEXT`, `INTENTS`).
- Remembering the scroll position, the app's own state, or reopening an app at launch: the phone owns the app.
- Keeping the phone awake, unlocking it, or changing a lock or screen-timeout setting (product promise).

## Decided (the person, 2026-10-28)

- A lone window keeps the short title "<App> (<phone>)"; the task label appears from the second window on (WIN-3, WIN-28).
- The cap is reported by the phone (`state.maxWindows`), 4 by default (WIN-32).
- ⌘` is ours: one "Next Window ⌘`" item scoped to the key app, AppKit's "Cycle Through Windows" removed; ⇧⌘` keeps the system's meaning (WIN-29, WIN-30).
- One Dock shim per app; its menu lists the open windows (WIN-26).
- Two windows of one app on one phone are intended, on request only (WIN-25, WIN-26).
