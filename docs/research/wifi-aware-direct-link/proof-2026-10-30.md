# Mac ↔ Android direct link over Wi-Fi Aware

Research and proof of concept · October 2026

## Summary

The Mac already contains a complete Wi-Fi Aware (NAN) implementation: a working `nan0` interface, the `wifip2pd` service, and the `WiFiAware` / `WiFiPeerToPeer` frameworks. Nothing needs to be added at the system level to make the radio work.

What is gated is **access**, in four layers: SDK availability, a restricted entitlement, a bundle allowlist, and a network-policy layer that only admits flows associated with the service's own network agent.

A working direct link has been established and measured:

- Mac publishes/subscribes through the private toolkit; the Galaxy S25+ uses the stock Android public API.
- A datapath (NDP) is established with a PSK passphrase; both ends get link-local NDI addresses.
- A bidirectional packet stream runs over the link with **0.2–1% loss and 10–16 ms average round-trip**.
- The stream remains stable with the two devices on **different LANs** (no IP path between them) and with Wi-Fi associated at both ends.

The packet path that works is a **BPF tap on `nan0` plus a userspace IPv6 stack**, which is independent of the network-policy layer. No system-level driver work is involved.

## 2. The four access layers

1. **SDK availability.** Every `WiFiAware` declaration is marked unavailable on macOS. Build flag: `-Xfrontend -disable-availability-checking`.
2. **Entitlement (`com.apple.developer.wifi-aware`).** The framework refuses to start without it; an ad-hoc signed binary carrying it is terminated at launch unless the AMFI check is relaxed for the session.
3. **Bundle allowlist.** `wifip2pd` keeps a list of accepted bundle IDs. Boot setting `wifiaware_allowlist=0` disables the list for the session (the service logs `Allow list disabled with boot arg`).
4. **Network policy.** Flows that are not associated with the service's network agent are refused on `nan0`; a raw socket returns `EHOSTUNREACH` and the system counter `TCP NECP not allowed` increments. This is a policy association, not a missing capability. Removing the interface's agent entries does not change it, and the policy-session interface is reserved for Apple-signed platform binaries.

## 3. Paths evaluated

| Path | Result |
| --- | --- |
| Public `WiFiAware` API on macOS | unavailable by SDK |
| Private `WiFiPeerToPeer` publish / subscribe | **works** |
| Datapath (NDP) with PSK passphrase | **works**, both directions |
| Raw socket bound to `nan0` | refused by the policy layer (`EHOSTUNREACH`) |
| Changing the flow-control setting | no effect |
| Removing interface agent entries | no effect |
| Adding a policy session from a normal binary | not permitted (platform binaries only) |
| Modifying the service binary | not needed; not attempted in the final design |
| **BPF tap on `nan0` + userspace IPv6** | **works** |

A useful side finding: `nan0` receives a link-local address but no matching `fe80::%nan0/64` route is installed. A per-peer host route (or a prefix route) is required regardless of the packet path used.

## 4. Working architecture

1. **Session helper** — a small ad-hoc signed helper carrying the Wi-Fi Aware entitlement. It publishes/subscribes, discovers the peer and establishes the datapath with a PSK passphrase.
2. **BPF bridge** — a privileged helper opens `/dev/bpf` on `nan0` and writes/reads Ethernet frames directly, supplying the header (`BIOCSHDRCMPLT`). This path is independent of the policy layer that gates sockets.
3. **Userspace stack** — lwIP or a compact reliable-UDP protocol over the tap; the app sees a normal socket or TUN interface.
4. **Routes** — the helper installs the peer route on `nan0`.
5. **Fallback** — at startup, probe the capability; fall back to LAN, hotspot or USB when the environment is not configured.

Phone side: stock Android `WifiAwareManager` — subscribe/publish, `setPskPassphrase`, then ordinary sockets over `aware_data0`. No root, no Shizuku, no special setup beyond Nearby Devices and location permissions.

Mac on the 2.4 GHz network, phone on 5 GHz; the Mac's address was moved to `10.99.99.2/24` for the test window so the two devices had no IP path to each other, with Wi-Fi associated at both ends.

## 6. What the setup requires

| Step | Detail |
| --- | --- |
| System Integrity Protection | off (developer configuration, Recovery) |
| Boot settings | `wifiaware_allowlist=0 amfi_get_out_of_my_way=1` |
| Privileged helper | LaunchDaemon, ad-hoc signed, carries the Wi-Fi Aware entitlement |
| Phone | stock Android app, Nearby Devices + location permissions |
| Network | Wi-Fi associated, but no shared LAN required |

```sh
# Recovery
csrutil disable

# back in macOS
sudo nvram boot-args="wifiaware_allowlist=0 amfi_get_out_of_my_way=1"
# restart, then install the helper LaunchDaemon
```

The expensive part is the AMFI setting: it relaxes code-signing checks for the whole machine and, on this machine, caused Java/Gradle to stop working. The rest is a normal privileged install.

Revert with:

```sh
sudo nvram -d boot-args
csrutil enable   # Recovery
```

## 7. Product guidance

- Ship the **capability plus a verified setup path** for power users, not a store app. The installer sets the boot settings, installs the helper, probes at startup and falls back cleanly.
- Keep the direct link as an **opportunistic transport** behind the same abstraction as LAN / hotspot / USB.
- Expect the default path to remain infrastructure Wi-Fi: the measured 209 Mbit/s and 5.5 ms on the router already cover 1080p60 screen sharing.
- Treat the mode as version-sensitive: probe at launch, never assume the policy behaviour across macOS releases.
- The remaining engineering work is throughput: a userspace stack and a real transfer benchmark above 1 Mbit/s.

## 8. Reproduction

Helper commands (`nanagent`):

```
list | add | del <if> [uuid]        inspect/update interface agent list
ping <if> <peer-ip> <peer-mac>      single echo over the BPF path
log  <if> <peer-ip> <peer-mac> <secs> <pps> <bytes> <file>
                                    continuous stream with per-packet log
block <if> <secs>                   temporary infrastructure-path block
setip / dhcp / manual               address changes for LAN-separation tests
```

Stream and watch:

```sh
sudo nanagent log nan0 <peer-link-local> <peer-mac> 600 100 1200 /tmp/nan-link.log
tail -f /tmp/nan-link.log
```

Phone counters, sampled on the phone:

```sh
adb shell 'while true; do set -- $(grep aware_data0 /proc/net/dev | tr -s " " | cut -d" " -f2,10); \
  echo "$(date +%H:%M:%S) $1 $2"; sleep 1; done'
```
